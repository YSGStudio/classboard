# PRD: 수업용 계층형 칸반 보드

- 토픽 슬러그: `kanban-class-board`
- 작성일: 2026-11-24
- 근거 문서: 개인용 칸반 보드 도구 개발 계획서, PRD 문서(Claude Docs) 최종본

## Summary

교사가 프로젝트 안에 칸반 보드를 깊이 제한 없이 계층으로 쌓고, 학생이 카드를 쓰고 옮기는 웹앱 MVP다. 와우아이디어스의 프로젝트-작업장 구조와 발산·변환·수렴 단계를 칸반 형식으로만 구현하고, 다섯 가지를 더한다.

1. 보드별로 학생을 골라 주는 읽기·수정 권한
2. 공용 보드의 학생별 카드 가리기
3. 보드 아래에 학생마다 하나씩 배당하는 개인 하위 보드
4. 보드별 평가 기준으로 학생 보드 전체를 평가하는 교사 피드백
5. 이미지·PDF·링크 미리보기

- 스택: Next.js(App Router) + TypeScript + Supabase(Postgres, Auth, Storage, Realtime)
- 계정: 교사는 구글 로그인, 학생은 교사가 발급한 아이디 + 4자리 숫자 비밀번호

## Problem And Goal

**문제:** 수업용 PBL 플랫폼(와우아이디어스 등)은 보기 형식과 기능이 많아 칸반만 쓰려는 교사에게 무겁다. 일반 칸반 도구에는 보드 계층, 학생별 권한·가리기, 학생별 보드 배당, 보드 단위 평가가 없다.

**목표:**

1. 한 학급(약 30명)이 한 프로젝트를 이 도구만으로 끝까지 진행한다.
2. 교사는 보드마다 어떤 학생이 보고 쓸 수 있는지 정한다.
3. 각자 발산 단계에서 학생은 다른 학생의 카드를 볼 수 없고, 교사가 공개할 때 한꺼번에 본다.
4. 교사는 보드마다 정한 기준으로 학생의 보드 전체를 평가하고 피드백을 공개한다.

## Users And Use Cases

| 사용자 | 유스케이스 |
| --- | --- |
| 교사 | U1. 구글 계정으로 로그인해 학생 계정(아이디·4자리 비밀번호)을 발급한다. 등록된 학생은 그 교사의 모든 프로젝트에 들어올 수 있다 |
| 교사 | U2. 프로젝트 안에 보드를 만들고, 보드 아래에 하위 보드를 필요한 만큼 계속 만든다 |
| 교사 | U3. 공용 보드에 가리기를 켜고, 학생들이 다 쓴 뒤 "모두 공개"한다 |
| 교사 | U4. 보드 하나를 칸반으로 그대로 쓰면서, 그 보드 아래에 학생별 개인 하위 보드를 만들어 한 명에 하나씩 배당한다 |
| 교사 | U5. 보드마다 학생을 골라 읽기 또는 수정 권한을 준다 |
| 교사 | U6. 평가 기준을 등록하고 보드에 붙인 뒤, 학생별 보드를 차례로 평가하고 공개한다 |
| 교사 | U7. 학생별 단계 진행과 평가 여부를 한 표로 본다 |
| 학생 | U8. 발급받은 아이디·비밀번호로 로그인해, 권한이 있는 보드에 카드를 쓰고 옮기며 이미지·PDF·링크를 첨부한다 |
| 학생 | U9. 공개된 평가 기준과 내 평가 결과·피드백을 내 보드에서 본다 |

## Pre-Work

아직 저장소가 없는 신규 프로젝트다. 구현 전에 다음을 준비한다.

- [ ] Next.js(App Router, TypeScript) 프로젝트 생성, ESLint·Prettier 설정
- [ ] Supabase 프로젝트 생성, 로컬 개발용 Supabase CLI 설치
- [ ] Google Cloud에서 OAuth 클라이언트를 만들어 Supabase Auth의 Google 제공자에 연결(리디렉션 URL 등록)
- [ ] 환경 변수 이름 확정
  - 앱: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`(서버 전용), `STUDENT_PASSWORD_PEPPER`(서버 전용)
  - 로컬 Supabase CLI: `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID`, `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET`
- [ ] 테스트 도구: Vitest(단위), Playwright(E2E), RLS·Storage 정책 검증용 SQL 테스트(pgTAP 또는 스크립트)
- [ ] 테스트용 시드: 교사 2명(A, B), 교사 A의 학생 30명, 프로젝트 1개

## Non-Goals

이번 MVP에서 하지 않는다.

- 칸반 외 보기 형식(Card 격자, Canvas 자유 배치)
- 카드 단위 평가, 학생 간 상호평가, 투표·별점
- 같은 보드의 회차별(중간·최종) 평가
- 발상기법 템플릿(PMI, SCAMPER, 5W1H), 프로젝트 복제
- 검색·필터, 댓글
- 평가·포트폴리오 엑셀·PDF 내보내기
- 모둠 단위 보드 배당, 개인 하위 보드 카드를 다른 보드로 보내기
- 부모 보드의 열·권한 변경을 이미 만든 하위 보드에 자동 반영하기
- 영상·오피스 파일 미리보기, 링크 영상 임베드 재생
- 학생이 직접 비밀번호 바꾸기, 학교 SSO 연동, 다수 교사 공동 운영

## Requirements

모든 권한 규칙(R2, R5, R6, R8, R10, R15, R16, R19, R20)은 화면뿐 아니라 서버(DB RLS, Storage 정책)에서 강제한다.

| ID | 영역 | 요구사항 |
| --- | --- | --- |
| R1 | 계정 | 교사는 구글 계정으로만 로그인하며, 처음 로그인하면 교사 계정이 만들어진다. 교사는 학생 계정을 하나씩 또는 CSV(아이디, 이름)로 일괄 발급한다. 아이디는 전체에서 유일하며 비워 두면 자동 생성된다. 비밀번호는 **4자리 숫자**로 시스템이 무작위 생성하고, 발급 직후에만 목록으로 보여 주며 인쇄·CSV로 내려받는다. 교사는 비밀번호를 재발급하고 계정을 비활성화한다. 학생은 아이디·4자리 비밀번호로 로그인하며, 같은 아이디로 5회 연속 틀리면 5분간 잠긴다. 학생 로그인 화면에는 구글 로그인이 없다. |
| R2 | 프로젝트 | 교사는 프로젝트(제목, 목표, 시작일, 종료일)를 만들고 수정·보관·삭제한다. 참여 코드나 프로젝트별 학생 추가는 없다. 교사가 등록한 학생은 그 교사의 모든 프로젝트(보관 제외)에 들어갈 수 있고, 다른 교사의 프로젝트는 볼 수 없다. 프로젝트 안에서 어느 보드가 보이는지는 R19를 따른다. |
| R3 | 보드 계층 | 교사는 프로젝트 안에 보드를 만들고, 어느 보드 아래에나 하위 보드를 **깊이 제한 없이** 만든다. 모든 보드는 그 자체로 칸반이다. 보드 목록은 접고 펼치는 트리로, 보드 화면 상단에는 경로(프로젝트 > 상위 보드 > 현재 보드)를 표시한다. 같은 부모 안에서 순서를 바꾼다. 프로젝트가 순차형이면 같은 부모의 형제 보드 사이에서 교사가 "열기"한 보드만 학생에게 열린다. 보드를 자기 하위로 옮겨 순환이 생기는 요청은 거부된다. |
| R4 | 열 | 새 보드는 발산·변환·수렴·실행·완료 5개 열로 시작한다. 교사는 열의 이름·색·순서를 바꾸고 열을 추가·삭제한다(1~8개). |
| R5 | 카드 | 카드는 제목(필수, 100자), 본문(2000자), 라벨, 마감일, 체크리스트, 첨부(이미지 JPG·PNG·GIF·WebP 10MB, PDF 20MB, 링크)를 갖는다. 작성자는 자동 기록된다. 학생은 수정 권한이 있는 보드에서만 카드를 쓰고, 자기 카드만 수정·삭제한다. 교사는 모든 카드를 수정·삭제한다. |
| R6 | 이동 | 드래그 앤 드롭으로 카드를 열 사이·열 안에서 옮긴다. 터치 기기에서는 "다음 단계로"·"이전 단계로" 버튼도 제공한다. 학생은 수정 권한이 있는 보드에서 자기 카드만 옮긴다. |
| R7 | 실시간 | 한 사용자의 카드·권한 변경은 같은 보드를 보는 다른 사용자 화면에 새로고침 없이 3초 안에 반영된다. 볼 수 없는 카드는 반영되지 않는다. |
| R8 | 가리기 | 공용 보드는 가리기 방식 끔/숨김/개수만/익명 중 하나를 갖고, 열마다 적용 여부를 정한다. 적용된 열에서 학생에게: 숨김=다른 학생 카드가 없음, 개수만=카드 수만, 익명=내용은 보이고 작성자는 숨김. 교사는 항상 전체와 작성자를 본다. 숨겨진 데이터는 학생의 API 응답에 포함되지 않는다. |
| R9 | 공개 | 교사는 "모두 공개"로 보드의 가리기를 즉시 끄고, "다시 가리기"로 이전 설정으로 되돌린다. |
| R10 | 개인 하위 보드 | 교사는 어느 보드에서든 "학생별 개인 보드 만들기"로, 선택한 학생(또는 전체)마다 그 보드 바로 아래에 하위 보드를 하나씩 만들어 배당한다. 부모 보드는 그대로 칸반으로 쓸 수 있다. 하위 보드는 부모의 열 구성을 복사하고 이름은 학생 이름이다. 기본 권한은 배당된 학생=수정, 다른 학생=없음이며 R19로 바꿀 수 있다. 나중에 등록된 학생에게도 자동으로 만들어진다. 개인 하위 보드 아래에도 하위 보드를 더 만들 수 있다. |
| R11 | 학생별 보기 | 교사는 보드별로 학생 × 열별 카드 수와 평가 상태(미평가/작성 중/공개됨) 표를 본다. 개인 하위 보드가 있는 보드에서는 각 학생의 하위 보드 카드 수를 보여 주고, 누르면 그 보드로 이동한다. |
| R12 | 활동 기록 | 카드의 생성·수정·이동·삭제마다 활동 기록(누가, 무엇을, 이전·이후 열, 시각)이 남고, 카드 상세에서 보인다. |
| R13 | 평가 기준 | 교사는 내 기준 목록에 기준(이름, 설명, 단계 2~5개: 단계명·점수·설명)을 만들고 수정·삭제하며, 프로젝트와 상관없이 재사용한다. |
| R14 | 보드별 기준 | 교사는 보드 설정에서 기준을 골라 붙이거나(순서 포함) 그 자리에서 새로 만든다. "학생에게 기준 미리 보여주기"를 켜면 학생은 보드 상단에서 기준을 본다. 개인 하위 보드는 부모 보드에 붙인 기준을 따른다. |
| R15 | 보드 단위 평가 | 평가는 (기준이 붙은 보드, 학생) 단위로 하나다. 대상은 그 보드에 개인 하위 보드가 있으면 그 학생의 하위 보드 전체, 없으면 그 학생이 그 보드에 쓴 카드 전체다. 평가 화면은 왼쪽에 대상을 읽기 전용으로, 오른쪽에 기준별 단계 선택과 서술형 피드백(2000자)을 보여 주고, 자동 저장·이전/다음 학생 이동을 지원한다. 카드마다 평가하는 UI는 없다. |
| R16 | 평가 공개 | 교사는 학생별 또는 보드 전체 "평가 공개"를 하고 취소할 수 있다. 공개 전에는 학생에게 평가가 없는 것처럼 보이고, 공개 뒤에는 자기 평가만 보드 상단에서 본다. |
| R17 | 기준 잠금 | 평가가 1건 이상 있는 기준은 단계를 수정·삭제할 수 없고, "복사해서 수정"만 가능하다. |
| R18 | 반응형 | 모든 화면은 360px 폭 휴대폰부터 PC까지 쓸 수 있다. 모바일에서는 열을 가로 스크롤한다. |
| R19 | 보드 권한 | 보드마다 기본 권한(모든 학생: 없음/읽기/수정)과 학생별 권한이 있다. 교사는 보드 설정에서 학생을 골라(여러 명·전체 선택) 읽기 또는 수정 권한을 주거나 회수한다. 학생별 권한이 기본 권한보다 우선한다. 없음=보드 트리에도 안 보임, 읽기=보기만, 수정=카드 작성과 자기 카드 수정·이동·삭제. 새 하위 보드는 부모의 권한을 복사해 시작한다(개인 하위 보드는 R10 기본값). 권한이 없는 보드의 하위 보드도 권한이 있으면 접근할 수 있으며, 트리에는 상위 보드 이름만 흐리게 표시한다. |
| R20 | 미리보기 | 이미지는 카드에 썸네일, 누르면 원본을 크게 보여 준다. PDF는 카드에 첫 페이지 썸네일, 카드 상세에서 페이지를 넘기며 보는 뷰어를 제공한다. 링크는 서버가 가져온 제목·대표 이미지·설명·도메인을 카드로 보여 주고, 가져오지 못하면 URL만 표시한다. 첨부 파일은 그 카드를 읽을 수 있는 사용자만 연다. |

## Acceptance Criteria

모든 AC는 시드 데이터(교사 A·B, 교사 A의 학생 30명, 프로젝트 1개) 기준이다. "학생 A/B/C"는 교사 A의 서로 다른 학생이다.

| ID | 요구사항 | 기준 | 검증 경로 |
| --- | --- | --- | --- |
| AC1 | R1 | 교사는 구글 로그인으로만 들어온다. CSV 30행으로 학생 30명의 아이디와 4자리 숫자 비밀번호가 발급되고 목록을 내려받는다. 중복 아이디는 거부된다. 학생은 아이디·비밀번호로 로그인하고, 틀린 비밀번호·비활성 계정·재발급 전 비밀번호는 거부된다. 같은 아이디 5회 실패 후에는 올바른 비밀번호도 5분간 거부된다 | E2E + DB 확인 |

## Technical Structure And Changes

신규 저장소라 기존 구조 변경은 없고, 아래를 새로 만든다.

### 스택

- Next.js(App Router) + TypeScript — 기본 스택 그대로. UI는 Tailwind CSS, 드래그는 dnd-kit, PDF는 pdf.js(`pdfjs-dist`).
- 데이터베이스: **Supabase(Postgres)**, 접근 계층은 `@supabase/supabase-js` + `@supabase/ssr`.
  - 근거: 저장소가 아직 없어 파일 근거는 없다. 사용자가 검토한 개발 계획서(6장)에서 로그인·실시간·행 단위 권한이 필요해 확정했다.
- 환경 변수: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`(서버 전용), `STUDENT_PASSWORD_PEPPER`(서버 전용). 서버 전용 키는 클라이언트 번들에 넣지 않는다.
- 파일: Supabase Storage 비공개 버킷 `card-attachments`(이미지 10MB, PDF 20MB).
  - 썸네일(긴 변 400px PNG)은 업로드 때 브라우저에서 만들어 함께 저장한다. PDF는 pdf.js로 첫 페이지를 렌더한다.
  - 파일은 서명된 URL(1시간)로만 연다.

### 권한 설계(RLS)

- 교사: 자기 프로젝트의 모든 행을 읽고 쓴다.
- 학생 보드 접근은 SQL 함수 `student_access(board_id)` 하나로 계산한다.
  1. 프로젝트 교사가 내 교사가 아니면 none
  2. board_permissions 행이 있으면 그 값
  3. 개인 보드의 owner면 edit
  4. 아니면 default_access

  상위 보드 권한은 상속하지 않는다(생성 때 복사만).
- `boards` SELECT: access ≥ read. 트리에서 접근 못 하는 상위 보드는 `get_board_tree(project_id)`가 이름만 돌려준다.
- `cards`
  - SELECT: access ≥ read이고 가리기 규칙 통과
  - INSERT: access = edit이고 보드가 열려 있음
  - UPDATE/DELETE: 자기 카드이고 access = edit
- "개수만"과 "익명"은 학생이 테이블을 직접 읽지 않고 `security definer` 함수 `get_board_view(board_id)`로만 얻는다.
- Storage 정책: 첨부 파일 읽기는 해당 카드를 읽을 수 있는 사용자만.
- `evaluations`: 학생은 student_id=본인 그리고 published=true일 때만. `criteria`는 연결된 보드의 show_criteria=true일 때만.
- 실시간: 카드·권한 행을 직접 구독하지 않고 `board_events`를 구독해 신호를 받으면 다시 조회한다(숨긴 내용이 이벤트로 새지 않게).

### 로그인

- 교사: Supabase Auth Google OAuth(`signInWithOAuth`). 콜백 `/auth/callback`에서 처음 들어온 사용자의 profiles 행을 role=teacher로 만든다.
- 학생 계정 생성: 교사의 Server Action이 service role로 Supabase Auth 사용자를 만든다.
  - 이메일은 내부용 `<login_id>@students.invalid`다.
  - Supabase 비밀번호는 최소 6자라 4자리를 그대로 쓸 수 없다. 그래서 `HMAC-SHA256(STUDENT_PASSWORD_PEPPER, login_id + ":" + 4자리)`를 실제 비밀번호로 쓴다.
- 학생 로그인: Server Action이 처리한다.
  1. login_attempts에서 잠금 확인
  2. 비밀번호 변환
  3. `signInWithPassword` 호출
  4. 실패 횟수 기록

  발급 비밀번호는 저장하지 않는다(재발급만 가능).

## Implementation Result Report Contract

1. **태스크 결과:** T1~T18 각각 완료/부분/미완료와 한 줄 설명
